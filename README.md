# Sparklet Android

Native Kotlin/Jetpack Compose client for Sparklet. See `AGENTS.md` for
architecture and the backend contract this app depends on.

## Status

Builds and runs on a physical device (2026-09-11). Verified from the command
line on macOS — `./gradlew :app:assembleDebug` → BUILD SUCCESSFUL, installed
via `adb install`, launches clean (cold start ~430ms, no crash, no errors in
logcat). That closes the question the previous status left open: the
Kotlin/Compose sources do compile, not just resolve.

Built: Custom-Tabs sign-in against the real mobile-auth contract, a paged
single-card feed screen backed by `GET /api/feed`, the two-POST
read-tracking flow against `/api/interactions` (tracking only the one card
actually settled on screen — see the comment in `FeedScreen.kt`, this was a
real integrity bug in the iOS client's earlier pass and is worth not
repeating here), a header stats row backed by `GET /api/profile`, and
quiz/guess/misconception/review answering (`QuizAnswerView.kt`,
`GuessAnswerView.kt`, `MisconceptionAnswerView.kt`, `ChallengeApi.kt` — this
is ahead of `sparklet-ios`, which still hasn't built that surface).

Sign-in, feed, stats header and challenge cards are all confirmed working
end-to-end against production on-device. **Read tracking was completely broken
until 2026-09-11** — two independent bugs, both silent, both now fixed and
verified on-device by watching XP increment (see "Read tracking" below). One rough edge: with the Sparklet PWA
installed, Chrome routes sign-in through the PWA rather than the Custom Tab —
it completes, but the detour is confusing. See "Testing sign-in" below.

`compileSdk`/`targetSdk` are `34` while the installed SDK has platform
`android-36`; AGP downloads platform 34 on demand, which is expected, not a
project bug.

## Building

A Gradle wrapper **is** now committed (`gradlew` + `gradle/wrapper/gradle-wrapper.jar`,
pinned to Gradle 8.13 — matching the `gradle-wrapper.properties` that was
already in the repo). It was generated with a standalone Gradle 9.3.1 in a
throwaway directory and copied in, so no local Gradle install is needed any
more. Command-line builds work:

```bash
export JAVA_HOME=/path/to/a/jdk17   # AGP 8.13 needs JDK 17+
./gradlew :app:assembleDebug
./gradlew :app:installDebug         # or: adb install -r app/build/outputs/apk/debug/app-debug.apk
```

First build is slow (~18 min cold, downloading Gradle and the dependency
graph); incremental builds are ~20s. Android Studio also still works —
open this directory directly and let it sync.

Note `gradle/gradle-daemon-jvm.properties` (generated by Studio) pins the
Gradle *daemon* to a JetBrains JDK 21 it will fetch via foojay. Builds
succeed with a plain JDK 17 in `JAVA_HOME` regardless.

## Pointing at a local backend

The API base URL is **no longer hardcoded in source**. It defaults to
production (`https://sparkletapp.com`) and is overridden by a Gradle
property, so pointing at a dev server never means editing — or accidentally
committing — a tracked file:

```properties
# local.properties (gitignored)
sparklet.apiBaseUrl=http://192.168.1.42:3001
```

```bash
# or one-off
./gradlew :app:assembleDebug -Psparklet.apiBaseUrl=http://10.0.2.2:3001
```

It reaches `AppConfig.apiBaseUrl` via `BuildConfig.API_BASE_URL`; see the
comment at the top of `app/build.gradle.kts`.

This replaced a real bug: `AppConfig.kt` had `http://10.0.2.2:3001`
hardcoded since the scaffold commit. `10.0.2.2` is the *emulator's* alias for
the host machine and resolves to nothing on a physical device, so every
device build failed every request. (The previous README claimed the value was
`https://sparkletapp.com`; it never was.)

Debug builds permit cleartext HTTP to any host
(`app/src/debug/res/xml/network_security_config.xml`), so a LAN IP needs no
extra allowlisting. Release builds keep the strict HTTPS-only config in
`app/src/main/res/xml/`. Use the port from the `sparklet` repo's
`npm run dev` (`PORT=3001`).

## Read tracking

The core loop — a card counts as read only after two `/api/interactions`
POSTs ≥4.5s apart by the server's clock — was **awarding nothing at all**
until 2026-09-11, while looking completely healthy from the client. Two
separate bugs, each silent:

1. **The `action` field never reached the wire.** `InteractionRequest`
   declared `action: String = "view"`, and kotlinx.serialization omits any
   property equal to its default unless `encodeDefaults` is set — which
   `ApiClient.json` did not set. The backend's zod schema requires `action`,
   so every POST 400'd, and `FeedViewModel.trackView` swallows all exceptions
   into `null` by design ("a missed read ping costs this card's XP, nothing
   else"). Result: zero XP, no streak, no spaced-repetition recall, no demand
   signal — with no error anywhere.

   Fixed by setting `encodeDefaults = true` **and** `explicitNulls = false`.
   The second half is not optional: with `encodeDefaults` alone, a null
   `dwellMs` serialises as `"dwellMs": null`, and zod's `.optional()` accepts
   `undefined` but *rejects* an explicit null — which would have 400'd the
   entry POST instead. `action` also no longer has a default, so the
   requirement is visible at the call site rather than resting on serializer
   config.

2. **The first card of every session was never tracked.** `FeedScreen`
   watched `snapshotFlow { pagerState.settledPage }`, which emits `0` at first
   composition while `items` is still empty; `getOrNull(0)` returned null, and
   `distinctUntilChanged()` then suppressed the page-0 re-emission once the
   batch arrived. Card 1 silently earned nothing, every session. Now the flow
   combines with `viewModel.items` and de-duplicates on item identity
   (`distinctUntilChangedBy { it.pagerKey }`), which also preserves the
   original guard against a pagination append re-firing a redundant POST pair.

Verified on-device: first card now tracks with no swipe
(`awarded=1, today=17`), each subsequent card tracks exactly once with no
duplicate card ids, and XP increments 17 → 18 → 19 → 21 across swipes.


## Testing sign-in

Exercised against production from a real device (Samsung Galaxy Z Flip 7,
`SM-F766B`, Android 16) on 2026-09-11. What is confirmed working:

- `GET /login?mobileScheme=sparklet-android` → 200.
- `POST /api/auth/mobile-exchange` with a bad code → `401
  {"error":"invalid or expired code"}`, matching the contract.
- The app launches Custom Tabs correctly, and `sparklet-android://auth`
  resolves uniquely to `com.sparklet.android/.MainActivity` (`cmd package
  resolve-activity` confirms no other app claims it).
- The cancellation path works: returning to the app without a redirect shows
  "Sign-in was cancelled." rather than hanging.

**Sign-in works end-to-end**, confirmed 2026-09-11: token persisted to
`files/datastore/auth.preferences_pb`, stats header live (streak + XP), feed
paging and a guess card rendering against production.

**But it takes an ugly detour when the Sparklet PWA is installed.** Chrome
hands the `/login` navigation out of the Custom Tab and into the WebAPK:

```
com.sparklet.android → chrome/IntentDispatcher → chrome/CustomTabActivity
  → org.chromium.webapk.<id>/H2OTransparentLauncherActivity   ← diverted here
  → SplashActivity → WebappLauncherActivity → SameTaskWebApkActivity
  → (sign-in completes inside the PWA)
  → sparklet-android://auth?code=…  → com.sparklet.android/.MainActivity
```

So sign-in happens in the *PWA*, not the Custom Tab, and the handoff back to
the native app still works — measured at ~3.7s from diversion to the
`sparklet-android://` intent landing. It is a UX problem, not a broken
contract:

- the user is bounced through a second Sparklet-branded app mid-sign-in;
- the first time, Chrome asks "Continue to Sparklet? This site wants to open
  the Sparklet app", which is actively misleading — both the PWA and this app
  are named "Sparklet", so it reads like it is offering the native app.
  Accepting makes the diversion sticky;
- if the user stops at the PWA screen instead of completing sign-in there,
  returning to the app shows "Sign-in was cancelled."

**Decision (2026-09-11): accepted as-is, not fixed.** It only reproduces with
the PWA installed, and the flow completes. Note the obvious-looking fix is a
trap — see decision 4 in `AGENTS.md` before reaching for the manifest
`scope`.

> An earlier revision of this file called this a hard blocker and claimed
> `sparklet-android://` never fires. That was wrong — see `MISTAKES.md`.

Also corrected while verifying: `AGENTS.md` said an unlisted `mobileScheme`
"400s at `/login`". It does not. `src/app/login/page.tsx` silently falls
through to an ordinary web login, and the 400 lives in
`/api/auth/mobile-complete`. So a typo'd scheme looks like a successful
sign-in in the browser while the app waits for a redirect that is never sent.
